# Due Diligence: AI Video Clipping and Publishing Business

This report evaluates the proposed business as of **November 18, 2026**, with later-crawled pages used only to confirm that the underlying programs and rules remained live immediately afterward. The central finding is straightforward: **the revised four-day MVP is on the right track, but the profitable version is not a fully autonomous “find clips and print money” system.** The technically automatable part—authorized source ingestion, transcription, clip selection, rendering, scheduling, publishing, duplicate prevention, cost tracking, and performance analysis—can be made highly automated. ## Executive verdict and the corrections that matter

**Go, but only as a supervised revenue pilot.** I would approve development of the narrow MVP, but I would not approve the original high-volume system yet. The first objective should be to prove one complete money loop:

**authorized source → compliant clip → approved social account → publication → Content Rewards submission → approval → qualified views → settled payout.**

Until that works repeatedly, increasing posting volume mostly increases processing cost, account risk, and operator workload rather than proven profit. This conclusion follows directly from Content Rewards' campaign-specific approval, minimum-payment, budget, fee, and payout rules, and from the publishing restrictions imposed by TikTok, YouTube, and Instagram. citeturn313123search0turn313123search6turn399436search2turn399436search4

The revised plan's **US$15–35/month infrastructure target is plausible for a narrow CPU-based pilot**, provided the user already has development access to Codex/Claude tooling, limits source-video minutes, uses a small VPS, performs serial CPU transcription/rendering, and avoids paid managed clipping services. The figure is a planning target, not a guaranteed bill. Hetzner's published entry-level x86 pricing places small cloud servers in roughly the required range before extras such as IPv4, VAT, backups, or higher CPU/RAM needs; Claude runtime cost can remain modest if transcript analysis is bounded and cached. citeturn220711search7turn104326search0

The four-day schedule is **reasonable for a working technical prototype in the hands of an experienced developer**, but not for proving a stable business. Account verification, source licensing, campaign admission, social-platform OAuth, disclosure capability, Content Rewards review, and actual payouts are external dependencies that can extend beyond the coding period. The architecture already acknowledges this distinction, and that distinction should remain explicit. fileciteturn0file0

The current plan should make four corrections. First, use **profit per qualified clip and profit per operator hour** rather than posting volume as the optimization target. Second, do not treat public YouTube/Twitch/Kick URLs as downloadable commercial source rights. Third, do not assume Buffer supports every campaign-required native paid-partnership field; direct Meta publishing is preferable when Instagram's native paid-partnership label is mandatory because Meta exposes that capability explicitly. Fourth, remove any suggestion that Content Rewards submissions can be batched automatically: I found official documentation for individual link submission within 30 minutes, but **no official evidence of a supported batch-submission API or automated batch endpoint**. citeturn399436search3turn313123search2turn584557view0

## Source discovery, lawful acquisition, and monetization rights

The system should separate **discovery** from **media acquisition**. A public URL can tell the system that a new video exists, but it does not automatically grant the right—or even a supported technical mechanism—to download, transform and monetize that video. That separation is one of the strongest design choices in the revised architecture. fileciteturn0file0

**YouTube** is suitable for authorized discovery and publishing. Its Data API supports searches and uploads through OAuth, but YouTube's API terms do not turn a public video into a freely downloadable commercial asset. Authorized source acquisition should therefore come from creator-provided originals, cloud folders, export feeds, or campaign-provided media. citeturn969493search2turn399436search6 For owned channels, the current Data API grants a default bucket of **100 `videos.insert` uploads per day**, which is far beyond a one-to-three-clips-per-day MVP. citeturn399436search5turn399436search6

**Twitch** offers a legitimate discovery path through its official Videos API and, importantly, now provides a supported clip-download flow where the token has the required channel/editor authorization. Those download URLs are temporary and access is permission-scoped. citeturn969493search10turn969493search11 I did not find a general official API granting arbitrary commercial download access to other creators' complete VODs; therefore full-recording ingestion should remain creator-provided or contractually supplied.

**Kick** lets creators download their own VODs from their dashboard, while its support documentation distinguishes that from downloading somebody else's VOD. Kick also allows clips to be created and downloaded where clipping is enabled, but the ability to technically download a clip is not a commercial license. citeturn482282search3turn482282search4 A Kick-based direct-client workflow should therefore have the creator supply the original VOD or a storage/feed export, rather than building an unauthorized VOD scraper.

Copyright permission and platform monetization eligibility are separate problems. YouTube explicitly says reused-content monetization rules apply independently of copyright permission; mass-produced, repetitive or minimally transformed content can be ineligible for channel monetization even when the uploader had permission. citeturn969493search0 That is particularly important for the user's idea: **captioning, vertical cropping and automated hooks alone should not be assumed sufficient to make a repost channel eligible for YouTube advertising revenue.** Owned-channel revenue should therefore be budgeted as **$0 until the channel actually qualifies and is accepted**.

TikTok's Creator Rewards rules create a similar constraint: eligible reward videos must meet originality and quality requirements and be at least one minute long; sponsored content is not treated as a normal Creator Rewards opportunity. citeturn204984search8turn204984search9 Paid Content Rewards clips therefore should not be modeled as simultaneously earning TikTok Creator Rewards income.

Cross-posting the **same authorized clip** to multiple platforms is technically possible where the campaign permits those destinations, but the system must store destination-specific captions, disclosure fields, aspect/length requirements and publication IDs. It should not assume that one platform's approval, rights, music license or monetization treatment automatically transfers to another. citeturn352287search0turn399436search2

## Clipping stack, publishing APIs, hosting, and unattended operation

The proposed custom stack is technically sound. **faster-whisper + Claude + FFmpeg** is the lowest-cost architecture among the options researched because transcription and rendering can run locally on CPU while Claude is reserved for editorial decisions rather than full video processing. The faster-whisper maintainer documents INT8 CPU modes, word-level timestamps and materially lower memory/runtime than the original Whisper implementation in benchmarked configurations. citeturn104326search6 Actual speed on a cheap VPS must still be benchmarked because published benchmarks use stronger CPUs than many entry-level cloud instances.

Claude is best used **transcript-first**, not by uploading entire long videos frame-by-frame. Current Anthropic pricing makes inexpensive models suitable for extracting candidate timestamps, hooks, campaign-fit checks and titles, with more capable models reserved for ambiguous clips; Anthropic also offers batch processing discounts for asynchronous workloads. citeturn104326search0turn104326search4 The software should cache transcripts and editorial results so the same source is never re-billed unnecessarily.

FFmpeg remains the correct rendering layer for deterministic cutting, rescaling, audio normalization and subtitle burn-in. The system should generate one known vertical template first and reject clips that fail decode, duration, audio, dimensions, caption timing or frozen/black-frame checks before they reach a publisher. This is an engineering recommendation consistent with the revised architecture's reliability design. fileciteturn0file0

**OpusClip** is worth benchmarking, but it is not the default choice for this low-cost MVP. Its API is available on selected paid tiers, with published API usage/capacity limits and credits tied to source-video minutes; a managed workflow becomes attractive when editing quality or development speed is worth more than the extra recurring cost. citeturn479834search0turn479834search4 For sustained low-volume use, the custom pipeline is cheaper and gives better control over campaign-specific rules.

TikTok is especially important because it disproves the old 48-posts-per-day assumption for a custom Direct Post integration. The platform documents a typical approximately 15-post-per-creator daily API limit, and its sharing guidelines expect a creator-facing experience with consent rather than an arbitrary private bulk uploader that blindly republishes other platforms' content. citeturn399436search2 The old volume-first plan is therefore not a sound default operating target even before content quality is considered. fileciteturn0file1

The revised plan's choice of **FastAPI + SQLite + Docker/service supervision** is appropriate for a single-owner, one-host MVP. PostgreSQL is unnecessary until there are multiple writers, multiple hosts or meaningful concurrency. n8n can be useful for notifications and simple orchestration, and its self-hosted Community edition can be used under its license for internal workflows, but inserting n8n between every state transition adds another failure surface without solving the hardest problem—the Content Rewards manual submission. citeturn276327search0turn276327search6

Reliable unattended operation requires more than a cron job. The system should persist source, clip, publication and submission states; create a publication intent before an external API call; reconcile unknown sends instead of blindly retrying; maintain uniqueness constraints so one clip cannot accidentally post twice; keep OAuth/API secrets out of source code; back up the database off-host; validate remote-media URLs against an allowlist; and stop publishing if rights, campaign terms, credentials, spending limits or required disclosure capabilities are uncertain. Those requirements are correctly emphasized in the revised architecture. fileciteturn0file0

## Payments, compliance, financial model, and break-even

Content Rewards currently routes withdrawals through **Whop**, and its current creator terms state that Whop handles withdrawal processing and related KYC. Whop requires identity/compliance verification to access payment functionality and can restrict payouts when KYC is incomplete or revoked. citeturn313123search10turn313123search28 Whop supports payout methods such as bank transfer, card/wire/check depending on jurisdiction and account configuration; therefore a Canadian or UK creator should verify the exact available withdrawal method inside the account before relying on it operationally. citeturn313123search30

Content Rewards does not promise that every view visible on Instagram, YouTube or TikTok is payable. The campaign's counted views, minimums, approval state, earning clock, cap and remaining budget control the actual payout. citeturn313123search18turn313123search19 This is the largest source of error in simplistic “1 million views × CPM” projections.

Tax treatment should not be hard-coded into the app. Content Rewards' current terms say payout and tax/KYC processes are handled through Whop and place tax responsibility on the participant rather than promising universal withholding. citeturn313123search26turn313123search28 A Canadian or UK operator should record gross earnings, platform fees, processing expenses, hosting costs, exchange rates and business expenses, then have the treatment reviewed under the operator's actual legal/tax status. The software should provide clean records rather than pretending to calculate final tax liability.

The following scenarios show why campaign thresholds matter more than infrastructure cost. They are **illustrative models, not earnings forecasts**.

| Scenario | Explicit assumptions | Monthly result before tax |
|---|---|---:|
| Low-volume failure case | 30 clips/month; $2 CPM; only 10 clips reach 5,000 qualified views; 20 earn $0 because they miss a hypothetical $10 minimum; 10% creator fee; $25 infra | 50,000 qualified views × $2 CPM = $100 gross; $90 after fee; **$65 cash contribution** |
| Moderate viable case | 30 clips/month; 15 qualifying clips averaging 10,000 views; $2 CPM; 10% fee; $25 infra | $300 gross; $270 after fee; **$245 before labor** |
| Strong pilot | 60 clips/month; every clip averages 10,000 qualifying views; $2 CPM; 10% fee; $25 infra | $1,200 gross; $1,080 after fee; **$1,055 before labor** |
| F1-like case | 30 clips/month; 10,000 qualified views each; $1.50 CPM; 10% fee; $25 infra; campaign budget remains available | $450 gross; $405 after fee; **$380 before labor** |

At a pure $2 CPM with a 10% creator fee and $25 infrastructure cost, mathematical cash break-even is only about **13,889 qualified views/month**. But that number is misleading when a campaign has a per-clip minimum. If a $2 CPM campaign requires each clip to earn at least $10, each paying clip would need roughly **5,000 qualified views** before that clip contributes at all. Campaign minimum semantics must therefore be imported from the actual brief rather than inferred. citeturn313123search2turn313123search0

Labor changes the economics quickly. If the attended Content Rewards workflow consumes ten minutes per published campaign clip, 30 clips/month consume roughly five operator hours. Valuing that time at $15/hour adds $75 to the economic cost; at $30/hour it adds $150. These are assumptions, but they demonstrate why **net contribution per operator hour** is the right optimization metric rather than views alone.

Legal and contractual risk is manageable only when the system records evidence. Every campaign/source should have a rights reference, terms version, permitted destinations, mandatory attribution, required sponsorship disclosure, prohibited content, allowed audio, expiration date and source-download method. Content Rewards' terms also permit anti-fraud screening and KYC/sanctions checks, and payouts can be frozen or disputed when submissions are flagged. citeturn313123search16turn313123search19

Instagram is attractive for the first campaign because its professional publishing API exposes a true **paid partnership** flag and sponsor IDs. citeturn399436search3 The application should never assume that `#ad` and a native platform label are interchangeable: use exactly the disclosure required by the campaign and applicable platform policy. F1, for example, publicly requires @Coinbase plus `#ad` or `#partner`; if a campaign additionally requires a native label, the publishing adapter must be able to set it or the post should be held for manual publication. citeturn352287search0

## Recommended MVP, automation boundary, and prioritized launch checklist

The best concrete first experiment is **Social Media Justice → authorized campaign source → Instagram Reels professional account**. Its November 18 economics were comparatively attractive at $2 CPM with substantial unspent budget, and its public brief explicitly identifies the content theme and source. citeturn352287search2turn352287search3turn242726search2 Before enabling automatic publication, however, the operator must join the campaign and verify the hidden requirements, confirm that the campaign actually provides a downloadable source or otherwise grants an authorized acquisition method, connect and verify the Instagram account, and test the exact sponsorship disclosures.

For this route, the automation boundary is:

| Step | Status | Reason |
|---|---|---|
| Discover a new file from an approved creator/campaign feed | **Automatic** | Straightforward once the authorized feed/storage location exists. |
| Download authorized media | **Automatic** | Only from approved creator/campaign storage or a documented permissioned API. |
| Transcribe with faster-whisper | **Automatic** | Local CPU workflow is viable; benchmark real host. citeturn104326search6 |
| Select candidate moments with Claude | **Automatic with hold rules** | Model can propose candidates; deterministic bounds/rules must validate them. |
| Render captions/layout with FFmpeg | **Automatic** | Deterministic media operation. |
| Campaign compliance check | **Partly automatic** | Mechanical tags/duration can be checked; ambiguous semantic/legal requirements still need a hold/review path. |
| Publish to Instagram professional account | **Automatic after setup** | Meta publishing API supports professional accounts. citeturn399436search4 |
| Apply native paid-partnership metadata | **Automatic via direct Meta integration where applicable** | Meta exposes sponsor IDs and paid-partnership flag. citeturn399436search3 |
| Submit published URL to Content Rewards | **Manual / attended** | Content Rewards requires submission within 30 minutes and publicly documents no API. citeturn313123search2turn584557view0 |
| Campaign approval | **External** | Campaign team controls approval. citeturn313123search6 |
| Pull verified campaign earnings automatically | **Not dependable for MVP** | No public submission/creator automation API was found; use verified manual entry/export where available. citeturn584557view0 |
| Profit calculations and alerts | **Automatic** | Based on recorded campaign data, costs and settled earnings. |
| Withdrawal/KYC | **Manual/external** | Whop handles KYC and withdrawals. citeturn313123search10turn313123search28 |

That makes the **production pipeline roughly 85–95% automatable**, depending on how clean the source feed and campaign rules are, but the **Content Rewards revenue loop is not 100% unattended**. This distinction is more important than assigning one automation percentage to the whole business.

The revised implementation should therefore remain close to the November 18 four-day plan, with one change in emphasis: **do not make Buffer mandatory for the first campaign test**. Implement a publisher interface and support Buffer for general publishing, but use direct Instagram/Meta publishing if the campaign requires native sponsorship metadata that Buffer has not been verified to expose. Buffer remains valuable as a generic one-channel publisher and its Free API limits are sufficient for one to three posts per day if polling is controlled. citeturn399436search0

The implementation sequence I would use is:

1. **Business gate:** create and KYC the Content Rewards/Whop account, connect the intended social account, join one campaign, save the full terms, verify remaining budget, and confirm actual source-file permission. If any of those fail, do not build campaign-specific automation. citeturn313123search10turn186808search7
2. **Publishing gate:** connect one Instagram professional account and perform one authorized test Reel through the chosen API, including every required disclosure. If the native disclosure cannot be set, keep publication manual until it can. citeturn399436search3turn399436search4
3. **Media gate:** process one representative 30-minute source through faster-whisper, Claude and FFmpeg; record transcription time, model cost, render time, RAM/disk use and resulting clip quality. citeturn104326search6
4. **Revenue gate:** publish one campaign-compliant clip, capture the real live URL and timestamp, submit it manually well inside the 30-minute window, preserve the receipt and wait for the actual approval/earnings state. citeturn313123search2turn313123search6
5. **Reliability gate:** run at one clip/day for at least several consecutive days, verifying no duplicate publications, restart recovery, alert delivery, cost limits and submission deadlines. Only then move to two and later three clips/day. This matches the revised architecture's acceptance logic. fileciteturn0file0
6. **Profit gate:** after enough clips complete their relevant earning/review windows, compare settled net revenue with hosting/API cost and operator time. Scale only campaigns with positive contribution per operator hour; pause weak routes instead of compensating with volume.

The **older volume-first architecture should not be used as the launch plan**. Its engineering ideas—durable state, PostgreSQL at scale, object storage, independent publisher adapters and robust retries—remain useful later, but its 48-posts-per-day target assumes both content supply and platform tolerance before either has been validated. fileciteturn0file1 TikTok alone makes that cadence unsuitable for its Direct Post API, and aggressive multi-platform posting would amplify the cost of unprofitable or noncompliant content. citeturn399436search2

The **revised four-day MVP is therefore a go**, subject to a hard Day-One commercial gate. If one real campaign, one authorized source, one eligible destination and one compliant publish path cannot all be verified, the build should stop at a semi-automated clipping/export tool rather than inventing unofficial integrations or scraping around platform restrictions. The sustainable business case is strongest when the same technical pipeline can serve **paid campaigns for short-term validation, direct creator retainers for predictable revenue, and owned channels for longer-term upside**, while treating platform monetization as zero until it is actually approved. citeturn969493search0turn313123search2
